# HydraCup v0.7.1

## 新增：從設定頁清除飲水紀錄

設定頁新增「10 清除飲水紀錄」，需再次輸入管理密碼確認。清除範圍：

- `logfs` 全部（飲水月檔 `/logfs/logs/drink-*.jsonl` 與尚未上傳的同步佇列）
- NVS `drink_ctr` 的今日累計與飲水次數——今日計數存在 NVS 而非 logfs，只清檔案會讓儀表板
  顯示一個沒有任何紀錄支撐的總量
- NVS `cloud_sync` 的 `evt_overflow` 溢位暫存，留著會把剛刪掉的事件放回佇列

**不會**刪除已同步到雲端的資料，也不動 `cloud_sync` 的 sequence 與 cursor（重置可能造成雲端
重複累加或拒收），校正值、WiFi 與其他設定同樣不受影響。

## 清除在下次開機時執行

端點本身不清除任何東西：它把要求記進 NVS、回應、然後重新開機，實際的清除發生在下次開機、
掛載檔案系統之前、任何 task 建立之前。

這個間接性是設計本身，不是實作細節。在系統運行中清除，等於要和每一個正在寫入這些資料的來源
賽跑：EventLogger 佇列裡的事件（包含已出佇列、正阻塞在檔案系統鎖上的那一筆）、計數器儲存的
佇列與重試路徑、開機時仍在讀取舊值的 NVS restore，以及 Cloud sync 在鎖內讀出、鎖外送出的批次。
每一項都需要各自的屏障，而檔案清除與計數清除之間仍然無法對「剛好在此時發生的一次飲水」保持
原子性。

先前的實作走的正是執行期清除，兩輪審查找出八個這樣的窗口，而且問題數是增加而非收斂——每補上
一個屏障就暴露出下一個。該版本已整個捨棄。

開機時這些都還不存在，清除因此是一條沒有併發的直線。`/logfs/logs` 與 `/logfs/cloud` 由
`EventLogger` 與 `CloudSyncClient` 在同一次開機的初始化中重建，不需要額外處理。

## 失敗與中斷的處理

執行順序為 **NVS 計數先、logfs 格式化後**，讓不可逆的一步排在最後：

- 計數抹除失敗 → 直接中止，一個位元組都還沒被刪，要求保留至下次開機
- 格式化失敗 → 計數已歸零但月檔仍在，同樣保留要求重試
- 要求旗標**最後才清除**，因此中途斷電只會再跑一次，不會回報一個沒做到的成功

歷史補傳進行中時，清除要求會被拒絕（`409`）——它會在回應與重開機之間繼續上傳並推進 cursor，
而那些歷史即將消失。

已知取捨：若旗標本身無法清除（NVS 持續性故障），每次開機都會重新格式化一次 logfs。那是更深層
的硬體問題，格式化是冪等的且 log 會明確指出，因此不另設重試上限。

## 安全

需要登入 session 與 CSRF token，**並在 body 再次提供管理密碼**——session 本身不足以授權一個
無法復原的操作。密碼以既有的 PBKDF2-HMAC-SHA256 雜湊比對，長度上限 128；驗證失敗計入與登入
端點共用的 IP 鎖定，避免這個端點成為繞過登入防護的暴力破解入口。
