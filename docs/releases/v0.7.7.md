# HydraCup v0.7.7

## 修正：webfs 下載緩衝區配置在 IRAM，一寫入就 panic

自 v0.7.0 引入 webfs OTA 以來，它從未成功過一次。serial 擷取到崩潰現場後，暫存器 dump
直接給出答案：

```
Guru Meditation Error: Core 0 panic'ed (LoadStoreError)
EXCCAUSE: 0x00000003        LoadStoreError
EXCVADDR: 0x40096bc0        出錯位址
A2      : 0x40096668        目的緩衝區
A12     : 0x00001000        4096 = OTA_WEBFS_CHUNK
PC      : 0x4000c325        ROM memcpy
```

`0x40096668` 位於 **IRAM**（ESP32 的 `0x40080000`–`0x400A0000`），而 IRAM 只允許 32-bit
對齊存取。`memcpy` 會做 byte 存取，因此第一批資料抵達、要複製進緩衝區時就 panic。

原因是配置緩衝區時只寫了 `MALLOC_CAP_INTERNAL`：

```cpp
heap_caps_malloc(OTA_WEBFS_CHUNK, MALLOC_CAP_INTERNAL)   // 錯
```

`MALLOC_CAP_INTERNAL` 只保證「不是 PSRAM、cache 關閉時仍可用」，**不保證可逐位元組存取**——
IRAM 完全符合前者卻不符合後者。要拿到 byte 可存取的記憶體必須加上 `MALLOC_CAP_8BIT`。

同樣的概念錯誤也出現在兩處 `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`：它們把不能當
byte 緩衝區用的 IRAM 也算進可用量，使更新前的記憶體檢查高估。一併修正。

## 這解釋了先前所有的失敗現象

- 崩潰發生在 `esp_https_ota_finish()` 之後，開機分割區已切換，所以韌體照常更新到新版本
- `saveLastOutcome()` 在正常路徑的最後才執行，panic 讓它沒機會執行——`last_outcome` 因此為空
- 崩潰在任何抹除或寫入之前，所以 webfs 有時完好（v0.7.4 邊抹邊寫之後）
- 從外部看就是「韌體燒完就重開」

`reset reason=4`（`ESP_RST_PANIC`）也在 v0.7.6 的開機記錄中確認了這一點。

## 先前兩個修正的定位

| 版本 | 修正 | 是否為本次崩潰的原因 |
|---|---|---|
| v0.7.2 | 下載跟隨轉址 | 否，但**必要**——沒有它下載根本不會開始，也就碰不到這個 panic |
| v0.7.4 | 邊抹邊寫 | 否，但**有價值**——它讓崩潰不再留下被抹空的分割區 |
| v0.7.6 | stack 10→16 KB | 否。當時的推論是 stack 溢位，實際不是；16 KB 保留作為餘裕，並非修正 |

## 驗證

- `pio run -e esp32dev`
- `pio test -e native`

依慣例，本修正需由 v0.7.7 執行下一次更新才會生效。
