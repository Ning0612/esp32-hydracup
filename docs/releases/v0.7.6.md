# HydraCup v0.7.6

## OTA task stack 由 10 KB 提高到 16 KB

v0.7.5 的更新中，韌體正常寫入，狀態顯示「開始更新網頁資源 · 0%」後裝置立刻重新開機，
webfs 未被更新也未被寫壞，而重開後 `last_outcome` 是空字串。

`saveLastOutcome()` 在正常路徑的最後才執行，沒有值代表**那段程式碼沒有被執行到**；正常路徑
還會在最終訊息停留 2.5 秒，而使用者並未看到。三項合起來指向：`_updateWebfs()` 開始後隨即崩潰。

最可能的位置是 `esp_http_client_open()` 內的 TLS handshake——那是整段流程中 stack 用量最深的
一點，而且緊接在韌體那次 TLS session 拆除之後。

原本 10 KB 的依據是「既有 `cloud_sync` task 以同樣大小跑完整 mbedtls TLS 已穩定」，但這個類比
並不成立：`cloud_sync` 一次只有一個 session，而 OTA task 在同一次執行中要建立**兩個**——韌體
一個、網頁資源一個——並且還要做 raw partition 寫入。姊妹專案 esp32-paper-frame 的 OTA worker
用 16 KB，而它**完全不碰 webfs**，做的事嚴格更少。

`CONFIG_FREERTOS_CHECK_STACKOVERFLOW_CANARY=y` 已啟用，因此若真為 stack 溢位，serial 會直接
指名 `ota_worker`。

## 診斷輸出

- `_updateWebfs()` 在關鍵步驟印出 log，包含每次轉址的狀態碼、content-length 與當下的
  stack 餘裕，崩潰時可從 serial 直接看出停在哪一步
- 開機時印出 `esp_reset_reason()`——正常 `esp_restart()` 與 panic／watchdog 從外部看完全相同，
  裝置都只是「換了版本重新出現」

## 參考：paper-frame 沒有 webfs OTA

`components/pf_ota/ota_worker_esp_idf.cpp` 明確註明 `webfs/imagefs are never touched here`，
其網頁資源僅能以 esptool 手動燒錄。轉址、抹除時序、raw partition 串流寫入這些問題，
都是 hydracup 自行新增此功能後才出現的，沒有既有實作可對照。

## 驗證

- `pio run -e esp32dev`
- `pio test -e native`

本版需由 v0.7.6 執行更新才能驗證 stack 是否為真正原因。
