# HydraCup v0.7.0

## 主要更新：OTA 一併更新網頁資源

v0.6.0 的 OTA 只寫 app 分割區，`data/` 底下的網頁資源位於 webfs，必須另接 USB 執行
`uploadfs`。本版把 webfs 併入同一個「立即更新」動作，設定頁按一次就會處理完韌體與網頁。

流程：
1. 先取得 release 的 `SHA256SUMS`。取不到就完全不動 webfs——沒有備援分割區，無法驗證的
   映像不該寫進去。
2. 寫韌體。失敗則整個更新中止，webfs 一個位元組都不會被碰。順序不可對調：先寫 webfs 再寫
   韌體，失敗時會留下「網頁比韌體新」的組合，而相容性契約只保證反向。
3. 比對 `SHA256SUMS` 裡 `hydracup-esp32dev-littlefs.bin` 的雜湊與 NVS 記錄的已安裝值。
   相同就跳過，不做無謂的抹除。
4. 需要更新時卸載 `/webfs`，抹除分割區，邊下載邊以 4 KB 為單位寫入並累算 SHA-256，
   寫完比對雜湊，相符才把新雜湊寫回 NVS。
5. 重新開機。

## 已知風險：webfs 沒有備援分割區

app 有 `app0`/`app1` 可以先寫再切換、失敗自動回滾；webfs 只有一塊，寫入是就地覆蓋，
而 384 KB 的映像也放不進 RAM 先驗證。因此**寫入途中失敗會使網頁資源損毀，需接 USB 執行
`uploadfs` 復原**。這是本功能明確接受的取捨。

失敗範圍僅限靜態頁面：API 由韌體提供，`/api/*` 在 webfs 損毀時仍可正常運作，裝置也照常
記錄飲水。狀態訊息會明確指出需要 USB 重新燒錄。

韌體寫入成功之後，無論 webfs 結果如何都會重新開機——新韌體優於舊韌體，即使網頁沒跟上。

## 與 HTTP server 的競態處理

httpd 在自己的 task 上服務靜態頁面，因此在卸載並抹除分割區的瞬間，可能正有請求處於
`fread()` 之中。靜態檔案的讀取現在受一把讀取鎖保護：OTA 先取得該鎖（等待進行中的傳送結束），
在仍持有鎖的狀態下把 webfs 標記為不可用，才釋放並卸載。通過檢查的請求因此不可能在卸載之後
才碰到檔案系統。若 10 秒內取不到鎖，本次就跳過 webfs——韌體已經寫入完成，不值得為此冒險。

`/api/*` 不受此鎖影響，更新期間狀態查詢照常回應。失敗路徑會嘗試重新掛載：校驗不符的情況下
分割區上其實是一份完整映像，通常仍可掛載成功。

## 其他

- `GET /api/ota/status` 新增 `stage` 欄位（`firmware` / `webfs`），指出目前正在更新哪一段。
- 設定頁的進度文字改為直接採用韌體回傳的 `message` 再附加百分比。所有面向使用者的文字都由
  韌體產生，因此比韌體舊的頁面仍能描述它沒學過的狀態。
- 首次由 USB `uploadfs` 安裝後，NVS 沒有已安裝雜湊的記錄，第一次 OTA 會重寫一次 webfs 即使
  內容相同。之後才會正確跳過。不改用「直接雜湊分割區內容」判斷，是因為 LittleFS 執行期間會
  改寫 metadata，實際位元組會與發佈的映像產生落差。

## 升級

可直接由設定頁「08 韌體更新」以 OTA 更新，本版起網頁資源會一併處理。

## 驗證
